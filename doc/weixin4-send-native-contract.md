# 4.1.15.13 发送任务与完成结果契约

本轮补充发送上下文的创建、登记、展示队列检查、协程等待和销毁链，并新增离线 `ReadTextSendCompletionSnapshot`。它只解码原生调用者已经取得的稳定结果，不创建消息、不提交任务、不调用微信函数。`call_succeeded` 仍只是原调用进入成功分支，不能证明服务端确认、对方送达或阅读。

## SendContext 的持有与销毁

`0x178f18f` 申请 `0x100` 字节块，设置 control 虚表 RVA `0x90d8088`，初始 strong/weak 两计数均为 1。对象从 control `+0x10` 开始，随后交给 `0x3981a30` 构造。构造函数设置对象虚表 `0x950a548`。

| SendContext 对象偏移 | 已确认用途与交叉证据 |
| --- | --- |
| `+0x08/+0x10` | 消息对象/控制块 pair；构造时复制，并对非空控制块的 `+8` 增计数；析构时释放 |
| `+0x18/+0x20` | `0x3981f20` 返回并移入的另一个 owner pair；具体载荷尚未确认 |
| `+0x38` | 32 字节 narrow-string，复制自消息对象 `+0xb0`；既有完整日志确认源字段是 `chat_id`，登记和展示队列检查均使用该字符串 |
| `+0x78/+0x80` | 初始化的结果 holder pair；`0x178f247..0x178f26a` 复制并持有，供 `0x179cb90` 等待/取得结果 |
| `+0xb8` | 保存传入 flag 的低字节；不为其补造业务名称 |

对象还持有其他 pair 和字符串。本表只描述本轮相关且确定的成员，不表示整个对象布局已经恢复。`0x3981a30` 和 `0x178f100` 均有对传入临时 owner pair 的释放路径，调用者也有对应复制/持有；因此既不能只传裸指针，也不能把字节复制当成正确的所有权移交。

销毁证据补全了以下链条：

1. control 虚表首项的叶函数 `0xaee0..0xaeed` 将 control `+0x10` 作为对象，调用对象虚表首项，第二实参为 0。这个 13 字节叶函数没有独立 `.pdata` 项，其边界来自原始反汇编并通过字节核验，不能称作 `.pdata` 恢复结果。
2. 对象虚表首项 `0x3987b30..0x3987b58` 先调用 `0x3987b60`，并仅在第二实参低位为 1 时释放对象地址。
3. `0x3987b60..0x3987d96` 释放消息 pair、结果 holder 等多个引用计数成员和 heap 字符串，使用 strong 归零后虚析构、再减少 weak 的模式。control 传入 flag 0 的路径与对象位于 control 内部的分配形态一致。

这些是原生对象的持有责任，离线解码器不执行其析构，不修改计数，也不把观察到的地址转换成可调用对象。消息对象原始构造、所有异常展开路径以及任务取消时尚存 callback 的持有责任仍需独立证据。

## 登记、展示队列与完成是三个阶段

日志和代码共同纠正了早期导航阶段的两个猜测：

| RVA | 证据支持的作用 | 关键日志 |
| --- | --- | --- |
| `0x1793050..0x17939d0` | `MessageManager::AddMessageSendContext`；按聊天标识散列并登记/追加上下文 | `0x90e6598` 完整函数名；`0x90e6610` add to send queue；`0x90e6658/0x90e66d8` 登记完成与 queue size |
| `0x1793c90..0x179541b` | `MessageManager::CheckPrepareShowQueue`；查找等待的上下文、检查进行中状态、驱动后续发送阶段 | `0x90e1998` 完整函数名；`0x90dfd78` 短名称；`0x90dcb70/0x90dcc10` 为 SerialStage 前后日志 |
| `0x179cb90..0x179cdb3` | 持有结果 pair，等待并取得 erased result，类型校验后复制调用者结果 | 明文 `bad cast`；直接调用 `0x39ce60 → 0x39f570` |

`0x1793c90` 的 `0x1794716` 调用既有 `0x17f3750`（StartSendMessageSerialStage）；后续还存在 SyncStage 完成日志、状态/键辅助函数、重新登记和递归检查队列等分支。不能把 `0x178f241` 改称等待调用，也不能把“登记完成”“展示准备完成”“某发送阶段结束”当作已发送到服务器。

真正的 await/get 链与联系人共享：

- `0x39ce60` 有明文 `coroutine.cpp` / `await`，先调用 `0x48bd30`，负返回值走异常；`0x39daa0` 返回 2 时进入 `await a rejected promise is not supported!` Fatal 日志路径。具体协程上下文检查/切换仍在这两个被调函数中。
- `0x39f570` 经锁相关辅助调用访问 holder `+0xc4`；为 0 时通过 `0x3a0930` 循环等待。非 2 分支返回 holder `+0xb8` 的 erased result；2 分支还要进行类型判断和异常转换。当前函数没有可见的超时参数，不能承诺可取消或有界返回。
- `0x179cb90` 对取得的 erased payload 做类型校验；缺失或不符会进入 `bad cast`。匹配后才复制结果。复制完释放临时结果 holder 的引用。

因此，静态已知的字段与函数地址仍不具备“可以从 HTTP 工作线程直接调用”的条件。具体线程要求、协程环境、终止/取消和错误传播必须分别确认。

## 调用者结果与离线 DTO

`0x179cb90` 将 erased payload 的数据复制成 **0x38（56）字节**的调用者结果。以下偏移以调用者结果缓冲为基址，不是 SendContext，也不是活动中的 promise holder。

| 结果偏移 | 新 DTO 字段 | 含义及限制 |
| --- | --- | --- |
| `+0x00/+0x04` | `status.status_word0/1` | 保留两个 uint32。外层 `0x54b1eb3..0x54b1ec0` 将二者 OR 后选择回调分支；独立错误域未知 |
| `+0x08` | `detail_string` | owned narrow-string 副本；原件类型校验后复制字符串，但不能据此命名为错误消息、正文或服务端描述 |
| `+0x28` | `payload_object_address` | 不透明载荷对象地址，仅作为观察值 |
| `+0x30` | `payload_control_address` | 相应控制块地址，可为 0；原生复制逻辑会持有非空控制块，离线读者不跟随或修改它 |

`ReadTextSendCompletionSnapshot` 复用原 `ReadTextSendResultSnapshot` 的 profile、空地址和状态读取规则，再以 checked add 定位字符串/pair。字符串受单串及总字符串预算中较小值限制。任何 `ReadError` 均清空整个输出，避免部分状态与旧数据混用。该 DTO 只拥有复制后的字符串，不拥有观察到的原生对象；返回地址不授予后续解引用能力。

旧 `ReadTextSendResultSnapshot` 保留原来的 **8 字节**输入契约。只有新入口要求完整选定的 56 字节字段；不把旧接口升级成读取未提供的后续内存。新旧入口的 `call_succeeded=true` 都只对应已有任务回调的成功分支，**不表示送达**。

`tests/weixin4_send_contract_tests.cc` 使用合成快照覆盖两个状态字、inline/heap 字符串、独立存储、内嵌 NUL、预算边界、空字符串/空 pair、未映射 opaque 地址、字符串损坏或缺页、末字段不可读、profile 门禁、地址溢出及错误清空，并验证旧 8 字节接口继续可用。测试不加载微信或调用任何发送函数。

## 未解决边界与下一静态候选

本轮没有恢复完整发送 ABI。仍未知：原始消息的具体类、vtable 和完整构造；所有完成/错误 callback 的注册与取消；结果原始错误域及 opaque payload；manager 的创建/销毁、账号代次和重登失效规则；协程/线程调度条件；可与本地任务相关联的服务端确认事件。任何日志 success 都不能替代这些证据。

下一轮可以按依赖顺序选择以下小范围工作，本轮没有启动这些分析：

1. `0x3981f20..0x398429b`：原件 `.pdata` 已确认；SendContext 构造时产生 `+0x18/+0x20` owner pair，优先明确它与后续阶段/回调的关系。
2. `0x1793c90` 已有报告中的直接 callee `0x17ef7a0` 和 `0x3986b40/0x3986b30/0x3986b10`：分别位于 SerialStage 后调用、分支条件、带常量 4 的调用和再次登记前的输出生成处，适合缩小阶段转换与最终结果发布者；这些辅助函数的实际语义仍待核定。后三个地址未命中独立 `.pdata` 项，应先有界反汇编核定叶函数边界，不能借用前一个 runtime-function 范围。
3. `0x48bd30..0x48c5fa`：原件 `.pdata` 已确认；与 `0x39daa0` 一起补充 await 的执行上下文和异常条件。`0x39daa0` 未命中独立 `.pdata` 项，先核定边界。复用已经完成的 `0x39ce60/0x39f570`，不重复分析。
4. 从既有 `0x54b1e10` 闭包 `+0x38/+0x40` 的赋值来源向上查消息构造链；从 manager 的已观察使用点查对象发布/失效。没有定位精确写入点前，不给出推测构造签名。

只有在原生 ABI、持有、线程、取消及账号代次条件闭合之后，才具备评估运行时接入的依据。当前产物是离线证据和结果解码器，`kRuntimeSupported` 保持 false。
