# 4.1.15.13 联系人任务契约

本项新增 `ContactStorageTaskRequestSnapshot` 和 `ReadContactStorageTaskRequestSnapshot`，从稳定快照提取**调用方已经提供的用户名列表**。它不创建或执行任务，不等待微信结果，不调用原生函数，也不枚举全部联系人。原有 `ReadContactQuerySnapshot` 仍仅解码低层联系人查询结果；两种快照没有被合并为一次完整查询。

## 可确定的输入与所有权

`0x2fabb40..0x2fabdee` 的 RCX 是存储上下文，RDX 是返回的两指针 holder 缓冲，R8 指向用户名向量。名称来自同一存储路径已还原的 `ContactStorageImpl::GetSessionInfoByUsernam…` 方法名前缀及 `0x2fb4520` 按用户名处理的调用链；未还原的方法名后缀不补猜。`0x1015900` 的反编译只列出两个参数，但汇编将传入的 R8 保留给 `0x2fabb40`，因此不能照抄反编译签名建立可执行函数指针。

| task 偏移 | 已确认的静态作用 | 读者处理 |
| --- | --- | --- |
| `+0x28/+0x30` | 从 storage `+0x20/+0x28` 复制的对象/控制块 pair；非空控制块 `+8` 增计数 | 不读取，不宣称其具体对象类型 |
| `+0x38/+0x40/+0x48` | begin/end/capacity 的 string vector；元素 32 字节 | 复制为 owned `usernames` |
| `+0x50` | 原始 storage 上下文地址 | 不读取或跟随 |
| `+0x58/+0x60` | 返回状态 holder 的对象/控制块 pair；构造和销毁均有引用计数路径 | 不读取，不伪装为已完成结果 |

构造器在 `0x2fabbfa` 请求 `0x68` 字节，`0x2fabc05/0x2fabc0c` 装入工作函数 `0x2fb4520` 和销毁函数 `0x2fba880`。`0x2fabc54..0x2fabc7b` 初始化 `+0x38` 向量并按 `(end-begin)>>5` 复制字符串。工作函数再次复制该向量，并将 `+0x28/+0x30` pair 移入局部变量、清零原位置。销毁函数按 32 字节步长释放用户名字符串及向量存储，再释放仍存在的两个控制块。这些交叉证据支持输入布局和原生持有责任；离线读者既不增减引用计数，也不复制整个 task 的原始字节冒充原生对象。

`usernames` 保留顺序、重复项、空字符串和内嵌 NUL 字节。这里没有建立“用户名必须符合某种文本格式”的业务规则；解码成功只表示选定输入结构可读。空向量也不代表“取全部联系人”。其他 task 字段可能不可读，读者不据此推断整个原生对象有效。

## 提交与结果：本轮纠正和边界

`0x2f9d610..0x2f9d6b4` 先取出并清零调用方的 task 指针，创建 `0x50` 字节外层闭包，其 `+0x48` 保存内层 task，工作函数为 `0x2f9d9b0`。`0x2f9d9b0..0x2f9d9fa` 取走并清零 `+0x48`，调用内层对象 `+8` 的工作函数指针，正常返回后调用 `0x107050` 清理该任务。异常展开的完整清理行为没有从这段正常路径推定。

`0x3a5750..0x3a57d9` 再建立 `0x30` 字节包装对象，将传入 task 移到 `+0x28` 并清零来源，读取全局 `0xb915428` 后调用 `0x3b5b10`。其原始 uint32 返回值经 `0x2f9d610` 返回到 `0x2fabb40`，但后者没有检查它。可以确认提交到全局调度对象的所有权移交链；真正接纳语义和具体执行线程仍在 `0x3b5b10` 及其调度对象内，不把移交成功当成任务已执行。

`0x1015a70..0x1015b9d` 复制 holder 的引用计数 pair，然后调用 `0x39ce60`、`0x39f570` 取得类型擦除结果，对实际类型作比较。匹配后返回所持对象 `+8`；无对象或类型不符则走 `bad cast` 抛出路径。新增后续函数证据明确了以下完成边界：

| 函数 | 已确认行为 | 限制 |
| --- | --- | --- |
| `0x39ce60..0x39cfb5` | 明文 `coroutine.cpp` / `await`；`0x48bd30` 返回负值时构造并抛出异常；随后 `0x39daa0` 返回 2 时记录 `await a rejected promise is not supported!` 和 Fatal 日志 | 不能把普通 HTTP 工作线程假定为已具备所需协程上下文；具体检查/切换机制仍在两个被调函数中 |
| `0x39f570..0x39f710` | 在 holder `+0x10` 的锁相关辅助调用后读取 `+0xc4` 状态；状态为 0 时通过 `0x3a0930` 反复等待，非 2 时返回 holder `+0xb8` 的 erased result | 此函数没有可见的超时参数；不能补造取消保证或把所有非零状态命名为成功 |
| 同一 getter 的状态 2 分支 | 对 erased result 再作类型判断，存在异常转换和抛出路径 | 完整错误类型与域尚未恢复，不将其等同于“联系人不存在”或统一空列表 |

`message-send-native-contract-pass1.json` 的 `0x179cb90` 也依次调用这两个 await/get 函数并作 `bad cast` 类型检查，因此该完成机制是联系人和消息共有的静态证据。调用者复制的 owner pair 支持结果取得期间的持有责任，但不证明一个未持有的原始地址可在任务停止、重登或对象销毁后继续访问。本轮不新增对该活动共享状态的离线读者，也不把观测到的偏移当作 live 线程同步方案。

**`0x1051c30` 不是等待函数。** 它构造空哈希容器：申请 `0x2c0` 字节哨兵节点，load factor 为 `1.0f`，初始 8 个桶。这与低层 `0x26e8250` 联系人结果的 `0x478` 字节节点不同。`0x1015900` 在类型校验后的聚合结果 `+0x40` 为 1 时复制其内容，否则返回新建的空容器。因此这个上层返回不能直接交给 `ReadContactQuerySnapshot`，也不能用“空列表”反推底层查询是否成功。

目前确定的是“带 `+0x40` 有效标记的聚合容器”和其外层类型擦除 holder。类型比较所使用的原件数据 `0xb1c9728` 不是普通明文 C++ 名称；没有恢复完整 C++ 模板类型，也没有为聚合行猜测字段。故本次不增加完成结果 DTO。

## 低层参数仅保留可证明的角色

| 入口 / 参数 | 已观察行为 | 尚不能命名的含义 |
| --- | --- | --- |
| `0x26e8250` / RCX | 含多个表对象引用的上下文 | 真实类及实例获取方式 |
| 同入口 / RDX | 写入结果容器及 `+0x40` 有效标记 | 不代表全量联系人覆盖率 |
| 同入口 / R8（反编译 a3） | 复制到随后进入查询构造链的对象 | 不能命名为用户名向量；完整条件类型未恢复 |
| 同入口 / R9（a4） | 继续传给 `0x26e8c70`，参与行解码相关调用 | 完整字段选择契约未恢复 |
| 同入口 / a5 | 非零选择 this `+0x90`，零选择 `+0x88` | 两种表的业务类别未知 |
| 同入口 / a6 | 结果有效时控制额外 `0x26e9630` 路径 | 不能称作缓存、强制刷新或本地标志 |
| `0x26e8c70` / a3 | 接收 `0x83820`，在行解码后调用并将返回值交给 map 插入 | 回调的完整类型未恢复 |

`0x2fb51b5` 的调用明确为 a5=0、a6=0，随后日志为 `get contact from db`。这不足以给两个参数取业务名。上层 `0x1019ce0` 仍存在 CGI 回退；完整用户名来源、全部联系人枚举入口、账号代次与 storage 失效规则仍未知。

## 验证

新增测试只链接本项目 `contact_contract.cc`、`memory_reader.cc` 和 `profile.cc`，不加载微信 DLL。已使用 MSVC `/std:c++17 /O2 /DNDEBUG /W4 /WX /utf-8` 独立编译并运行通过。测试在 `NDEBUG` 下仍执行检查，覆盖：

- inline/heap 字符串、顺序及重复项、内嵌 NUL、解码后独立存储；
- 未使用容量不被当作输入，未知 vtable/owner/storage/result 字段不被读取；
- 三项 profile 校验均先于任何内存读取；
- 空向量、数量/单串/总串预算边界、倒置/残缺/越界向量；
- 损坏后项、缺失内存、字符串终止符错误、地址溢出和错误清空输出。

这些验证只针对稳定快照读者。没有可调用 ABI、原生调度器实现、live reader、hook 或完成状态承诺；`kRuntimeSupported` 维持 false。
